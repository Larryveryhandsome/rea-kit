# LINE 群組命名與客戶代碼

群名是給人看的標籤；系統認人靠「群組 ID ↔ 客戶代碼」登錄表。
所以舊群不一定要改名也能正確運作——真正要改的，是把客戶隱私寫在群名上的那些。

## SOP

1. **讀前綴表**：預設 `買`、`賣`、`租`；租戶可改成 `{店名}買`、`{店名}賣` 這種，或加 `出租`、`承租`、`{內部前綴}`。另讀「靜默關鍵字表」（同業、總部、加盟體系、公會等群）。
2. **對登錄表**：每個群先查「群組 ID ↔ 客戶代碼 ↔ 類型 ↔ 狀態」。路由、去重、停推一律以登錄表為準。
3. **新群**：判斷類型（判斷要點 C）→ 發新代碼（判斷要點 B）→ 產生建議群名（判斷要點 A）→ 交給仲介自己在 LINE 改名。
4. **既有群**：檢查群名有沒有禁放資訊、前綴和登錄表類型是否一致、代碼是否一致，列出建議。
5. **群名被改**（群裡任何人都能改）：不改代碼、不改路由；只重新檢查類型，衝突就標「待確認」。
6. **交出建議清單**。改群名由仲介自己做；寫登錄表需要仲介確認後由工具執行。

## Decision points（判斷要點）

### A. 群名格式與禁放資訊

建議格式：`{交易前綴}／{需求簡稱}／{稱呼}／{客戶代碼}`

- **交易前綴**：放第一段，取自前綴表。
- **需求簡稱**（可省略）：區域或物件類型，例「東區透天」「市區兩房」。
- **稱呼**：客戶自己選的暱稱，或「姓＋先生／小姐」。
- **客戶代碼**：固定放最後一段。
- 分隔符號統一用一種（建議 `／`）；系統解析時 `／`、`/`、空白都要吃得下。

**群名禁放**（客戶和群裡每個人都看得到群名，也會被截圖、轉傳）：
- 預算、總價、月租、出價、自備款。
- 全名、電話、身分證、門牌地址、LINE ID、Email。
- 內部標記：VIP、分級（A/B/C/D）、成交機率、評語、轉介來源的公司或人名。
- 別人的資訊（介紹人、家人的全名）。

這些放在系統的客需卡與客戶欄位裡，只有仲介看得到。
**群名裡的數字永遠不是預算來源**；預算只從客需卡取。

### B. 客戶代碼

- **格式**：`{類型字母}{三位流水號}`。預設 買＝A、賣＝B、承租＝C、出租＝D、屋主（尚未委託）＝N；字母表跟著前綴表設定，**一經發出就不改**。
- **位數固定**：A001、A012；不要混用 A01、A0012。
- **只往上長**：新群＝該字母目前最大號＋1；舊號永不重用、永不重編。重編會讓代碼搬到別人的群：稱呼叫錯人、去重鍵位移、歷史紀錄變孤兒、所有客戶被重推一輪。
- **寫入前安全檢查**：既有每一筆的欄位必須完全相同，否則中止不寫；寫入前先備份，只留最近幾份；讀→算→寫全程上鎖，避免和其他程序互相覆蓋。
- **稱呼取自這個群自己的群名稱呼段**，不從別的代碼沿用。稱呼撞到已經在用的 → 先留空待確認（避免兩個客戶共用去重鍵）。
- **同一人又買又賣** → 兩個代碼（例 A 一個、B 一個），最好兩個群。不要把賣方需求塞進買方代碼。
- 解析預算時要忽略代碼段，代碼的數字不是預算也不是年份（`customer-need-structuring` 已規定）。

### C. 判斷群組類型（買方／賣方／租方／內部／靜默／未分類）

1. **只看第一段**，對前綴表、**最長的先比**：「出租」先於「租」、「承租」先於「租」。後面段落出現「賣」「租」字不算（可能是地名、店名或需求描述）。
2. **登錄表已有類型 → 以登錄表為準**。群名前綴和登錄表不一致 → 標「待確認」，期間不自動推。
3. **交叉檢查**：客需卡的交易別、對話關鍵詞（「我要賣」「委託」「開價多少可以賣」 vs 「想買」「預算」「想租」）。互相矛盾 → 待確認。
4. **內部群**（團隊、行政、廠商）：用內部前綴或登錄表標記；不收客戶物件，也不用對客戶的語氣。
5. **靜默群**（同業、總部、加盟體系、公會）：群名命中靜默關鍵字 → 官方帳號一律不發話。
6. **未分類**：沒有前綴、看不出類型 → 不自動推、不使用內部語氣、列入待確認。
7. **團隊版**：夥伴負責的客戶群，可在第二段放 `{成員代稱}` 標示承辦人；不放公司或品牌名。

- **賣方（屋主）群絕不收買方物件推播。**
- 判斷時用 LINE 當下的群名（或登錄表最新類型），不要用試算表裡的舊群名——群改名之後，舊名會對到錯的群。

### D. 改名規則

- **改名不改代碼、不改群組 ID**。登錄表只記「類型與變更時間」，不長期保存群名原文（群名常含客戶稱呼）。
- **交易類型改變**（買方後來要賣）：開新代碼，最好開新群；舊代碼標結案。
- **結案／成交**：在系統欄位標結案，停推以系統狀態為準。群名可以加結案標記（例 `已成交／…`）方便人看，但**只改群名不算停推**。
- **客戶自己改名、前綴不見** → 維持登錄表類型，通知仲介確認，不自動改回。
- **優先改**含禁放資訊的群；其他舊群可以慢慢改。
- 改名建議一次列一批給仲介，不要一群一群催。

## Checklist（檢查清單）

- [ ] 前綴表（含自訂前綴、內部前綴、靜默關鍵字）已讀取。
- [ ] 每個群都有 群組 ID ↔ 客戶代碼 的對應。
- [ ] 群名沒有預算、全名、電話、地址、內部標記。
- [ ] 類型判斷只看第一段、最長前綴優先，並和登錄表、客需卡交叉檢查。
- [ ] 新代碼＝最大號＋1、位數固定；既有代碼沒有被重編或重用。
- [ ] 賣方群、內部群、靜默群不在買方推播名單。
- [ ] 未分類與待確認的群不自動推。
- [ ] 沒有改 LINE 群名、沒有直接寫登錄表。

## Template（範本）

```text
群組命名檢查（{日期}）
前綴表：買＝{…}／賣＝{…}／租＝{…}（出租＝{…}、承租＝{…}）／內部＝{…}｜靜默關鍵字：{…}

要先改名（群名含禁放資訊）
- {客戶代碼}：目前群名（已遮蔽）「{買／市區＊＊＊＊萬兩房／＊＊＊}」｜含：{預算／全名／電話／內部標記}
  建議改成：「{買／市區兩房／王先生／A0xx}」

新群（建議代碼與群名）
- 群組 {群組代號}：類型 {買}｜依據：{第一段前綴／客需卡／對話}｜建議代碼 {A013}
  建議群名：「{買／東區透天／王小姐／A013}」

類型待確認（期間不自動推）
- {客戶代碼}：{群名前綴是賣，但登錄表是買／對話出現委託字眼}

代碼一致性
- 位數不一致：{…}｜稱呼重複：{…}｜登錄表缺漏：{…}

外部動作：無；群名由仲介在 LINE 自己改，登錄表要仲介確認後由工具寫入。
```

## Output requirements（輸出要求）

- 先列「要先改名」，再列新群、待確認、代碼一致性問題。
- 每個類型判斷都寫依據（第一段前綴、登錄表、客需卡、對話關鍵詞）。
- 回報現有群名時遮掉禁放資訊（數字與全名用 `＊`），報告內以客戶代碼稱呼客戶。
- 建議群名只用合成或客戶自選的稱呼，不得含禁放資訊。

## Test cases（測試案例，全部為合成資料）

**T1 — 新買方群**：群名「買／東區透天／王小姐」，登錄表 A 字頭最大號是 A012。期望：類型＝買；代碼 A013；建議群名「買／東區透天／王小姐／A013」。

**T2 — 禁放資訊**：群名「買／市區 1500 萬兩房／林測試／VIP」。期望：列入「要先改名」（預算、全名、內部標記）；建議「買／市區兩房／林先生／{代碼}」；1500 不寫進客需卡（預算只從客需卡來）。

**T3 — 最長前綴**：前綴表有 買／賣／租／出租／承租。群名「出租／東區店面／李先生」與「承租／套房／張小姐」。期望：第一個＝出租（不是租），D 字頭；第二個＝承租，C 字頭。

**T4 — 後段出現賣字**：群名「買／賣場附近兩房／周先生」。期望：類型＝買（只看第一段）。

**T5 — 客戶改了群名**：登錄表 B005（賣）；客戶把群名改成「家族看房群」。期望：維持「賣」、代碼不變、標待確認；期間不自動推。

**T6 — 重編防呆**：工具提議把既有 A003 改指到另一個群。期望：中止、不寫入，回報「既有代碼被動到」。

**T7 — 未分類**：群名「週末聚餐」，登錄表裡沒有。期望：未分類、不自動推、不使用內部語氣、列入待確認。

**T8 — 只改名不算結案**：業務把群名改成「已成交／…」，但系統狀態仍是追蹤中。期望：提示到系統標結案；只改群名不算停推。

## Acceptance criteria（驗收標準）

- 建議群名永遠不含預算、全名、電話、地址、內部標記。
- 既有代碼永不重編、不重用；新代碼可預期（最大號＋1）。
- 類型判斷可重現、附依據；有衝突一律待確認、不自動推。
- 賣方群、內部群、靜默群不會被標成買方推播對象。
- 沒有宣稱已改群名或已寫入登錄表。
