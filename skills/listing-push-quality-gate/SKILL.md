# 物件推播品質關卡（自動送／待審／不可送）

`listing-need-matching` 回答「哪件適合這位客戶」；本 Skill 回答「這件**現在**能不能送到客戶手上、用哪條路送、送完怎麼記帳」。
分數只決定**先送誰**，不決定**能不能送**——能不能送只看下面的硬關卡。

## SOP

1. **先分收件對象**：客戶（買方／承租方的客戶群或一對一）或內部（租戶本人、審核群、團隊內部群）。內部收件人**不進本關卡**，直接交內部通知（判斷要點 D）。
2. **確認穩定鍵**：收件人要有群組 ID 或客戶代碼。鍵是空的 → 不可送。不准用客戶名字或群名當鍵。
3. **跑硬關卡**（自動送必須全部成立；任何一條讀不出來＝不成立）：
   - **G1 客需明確**：區域＋預算都有。來源三選一：客需卡（客戶明講）、仲介手填／鎖定的需求、客戶在租戶自己系統存過的搜尋條件。仲介手填優先。
   - **G2 對象類型相符**：只推買方／承租方客戶群。賣方（屋主）群、內部群、同業群、未分類群一律不可送（分類見 `line-group-naming`）。交易別也要相符：租屋客戶不收買賣物件，反之亦然。
   - **G3 新鮮度**：配對產生時間（或物件最後確認在售時間）距今 ≤ 7 天。沒有時間 → 不可送。
   - **G4 可點連結**：要有客戶點得開的物件連結。絕不推只有物件編號的死訊息。
   - **G5 價格 vs 預算**：物件價格 ≤ 預算 × 容許倍數（預設 1.1，租戶可調）。
   - **G6 停推訊號**：客戶近 60 天說過不看／已買到、已退群、被標結案 → 不可送（規則見 `customer-followup-triage`）。
   - **G7 未曾駁回**：同一客戶 × 同一物件被駁回過 → 永不再送。
   - **G8 未曾送達**：同一客戶 × 同一物件已經 `sent` → 不重送。
   - **G9 每人份額**：同一客戶今天已送 1 件、本月已送 4 件 → 今天／本月不送（不移除，下一輪再評）。
   - **G10 時段與總額度**：只在 08:00–21:00 動客戶訊息；推播預算該級本月還有額度（只詢問，不記帳）；租戶設的每日總上限未滿。
4. **分桶**：自動送／待審／不可送／本輪暫緩（判斷要點 A–C）。
5. **排序**：同一輪有多件可送時，依「客戶談到哪一步（議價、帶看 > 需求明確 > 初詢 > 還沒開口）＋多久沒出聲（越近越前）＋配對多新」排。不是先進先出，也不是後進先出。每日總上限到了，其餘留到明天。
6. **交工具層送出**，依回傳三態記帳（判斷要點 E）。
7. **審核人按「送」那一刻重驗**（判斷要點 F），任一項不過 → 不送，並告訴審核人原因。
8. **G1 不過的客戶**進「需補客需」名單：不推、不排審；每週彙整一次交給負責業務去補問。

## Decision points（判斷要點）

### A. 自動送（全部成立才算）

- G1–G10 全過，**而且**租戶已把「物件推播」設為自動（產品預設是逐則審）。
- 自動路徑是 **fail-closed**：預算、價格、時間、連結任一讀不出來，就不自動送。待審路徑可以讓人看了再決定，自動路徑不行——自動送出去就收不回來。
- 客戶分級 D（從沒回過）不自動送（見 `customer-followup-triage`）。
- 客戶 7 天內正在跟業務來回對話 → 本輪不自動插話，讓業務自己講（可轉待審，由業務決定要不要附上）。

### B. 待審（沒有違反硬關卡，但需要人判斷）

- 租戶把物件推播設為逐則審。
- 客需有區域＋預算，但**物件價格讀不出來**（人點開連結就看得到）。
- 客需卡有和這件物件相關的 `conflicting` 或低信心欄位（例：房數前後說法不一）。
- 租戶選了「嚴格預算」：價格介於預算與預算 × 1.1 之間。
- 客戶是 D 級或正在跟業務對話：讓人決定要不要手動送。
- 待審＝**排隊中**，不是已推。

### C. 不可送與本輪暫緩

| 情況 | 處置 | 燒去重？ |
|---|---|---|
| G1 缺區域或預算 | 不推、不排審、從候選拿掉；客戶進「需補客需」名單 | 否 |
| G2 對象類型或交易別不符 | 不可送 | 否 |
| G3 超過 7 天 | 不可送（物件可能已下架，客戶點進去看到「已售出」比不推更傷） | 否 |
| G5 超過預算 × 容許倍數 | 不可送，**也不留給審核**（不值得人花注意力） | 否 |
| G6 停推、G7 駁回過、G8 已送過 | 不可送 | — |
| G4 連結還沒解出 | **本輪暫緩**，下一輪解出再評 | 否 |
| G9 每人份額、G10 時段／額度／每日上限 | **本輪暫緩**，不移除 | 否 |

### D. 內部收件人永遠不走審核閘

- 給租戶本人、審核群、團隊內部群的訊息（**包括「請你審核」的那張卡本身**）直接送。否則審核卡也被攔下來等審核，系統轉不動。
- 內部控制通道（本人、審核群）的額度與客戶推播**分開算**、彼此也分開。審核群若被歸進客戶額度，會被客戶推播吃光，而且是無聲失效。
- 月配額結構上就是 0 的內部例行日報：**不排隊、不問人**，要看時打字問、用回覆（不計額度）回。問一件註定送不出去的事，是在浪費審核人的注意力。

### E. 三態結果與去重（只有真的送到才燒去重）

| 狀態 | 意思 | 寫「已推」去重？ | 算每人每日／每月？ | 扣推播預算？ |
|---|---|---|---|---|
| `sent` | LINE 確認收下 | 是（客戶 × 物件，永久） | 是 | 是 |
| `queued` | 已核准（自動或人按），但還沒送出：額度用完、休息時段、每日上限 | 否，只佔「處理中」位 | 否 | 否 |
| `held` | 等人審 | 否，只佔「處理中」位 | 否 | 否 |

- 「處理中」位只用來防止同一則重複排隊；作廢或失敗就釋放。
- 任何「其實沒送、卻回傳成功」的捷徑（例如對某類群直接回成功）一律算 `failed`，不准記 `sent`。報表上的「今天推了幾件」只數 `sent`。寧可少報，不可謊報。
- `rejected`（審核人按不送）寫**永久黑名單**：同一客戶 × 同一物件永不再進候選，不是 7 天後再來一次。租戶可以手動解除。
- `failed`（LINE 拒收）不燒去重，留原因。看到額度用完（429）就**整輪停止**，不要一直重敲。
- `expired`（作廢）一定留痕，不默默丟。

### F. 審核當下重驗

佇列存「重建卡片需要的最小資料」（客戶鍵、物件 ID、排隊時的價格與客需卡版本），**不存凍結的整張卡**。按「送」時重查：

1. **物件還在售嗎？** 最新物件清單找不到、標下架或成交 → 取消。
2. **價格變了嗎？** 重算 G5：降價可以送，卡片用新價格；漲到超出容許 → 取消。
3. **連結還能用嗎？**
4. **客戶狀態變了嗎？** 新的停推訊號、退群、結案、降到 D、客需卡改版 → 取消或重新配對。
5. **今天這位客戶的份額還有嗎？** 沒有 → 轉 `queued`，不是 `sent`。
6. **等待時效**：物件推播的 `held`／`queued` 超過 **24 小時**自動作廢（`expired`）。作廢後如果仍然合格，下一輪會重新評估。

### G. 實戰鐵則（實際系統踩過的錯，已改寫成通用規則）

1. **價格只從物件本身的欄位取**，絕不從「整包資料」搜數字。整包裡可能含群名或客需，等於拿預算跟自己比，整道關卡變成空的。
2. **單位**：買賣預算用萬、租屋用元／月。月租數字絕不能當「萬」比價（會把上億物件推給租客）。買賣預算低於 50 萬多半是解析錯 → 當作讀不出來。
3. **群名或客戶代碼裡的數字不是預算**；預算只從客需卡取。
4. **同一把鑰匙**：每人份額、去重、停推、駁回黑名單全部用同一個穩定鍵，讀寫兩端用同一條公式。用名字當鍵，同名或空名的客戶會共用一桶，互相把物件「燒掉」。
5. **給審核人看的卡片內文只放客戶本來就會看到的內容**（區域、標題、價格、坪數、連結），不放群名、預算、分級。萬一卡片退成純文字，內部欄位不能跑到客戶眼前。
6. **給客戶的開頭稱呼不可取自群名片段**，否則會出現「店面預算您好」這種句子。
7. **待審容量只算客戶物件卡**；內部訊息不准把客戶物件卡擠出審核人一次看得到的範圍。客戶看得到的排前面。
8. **每張待審卡的指紋要各自不同**（地址＋標題），佇列編號要含收件人；否則同一件配給兩位客戶時會撞號互蓋，有人的卡片無聲消失。

### H. 與產品既有程式的對照

- 閘門、等審、作廢、回覆補送：`adapters/line/push_gate.py`。每日每人 1 則物件推播、各級配額、控制通道每日上限：`adapters/line/push_budget.py`。本 Skill 定義**判斷規則**，不重寫閘門。
- 程式預設值與本 Skill 不同時，以租戶設定為準，並在輸出註明。目前已知差異：等審時效預設 3 天（本 Skill 建議物件推播設 1 天）；每人每月 4 件、駁回永久黑名單尚未在程式裡（呼叫端要自己檢查）。

## Checklist（檢查清單）

- [ ] 收件人有穩定鍵；內部收件人已分流，沒有進審核閘。
- [ ] 客需區域＋預算都有；缺的人進了「需補客需」名單。
- [ ] 對象是買方／承租方客戶群，交易別相符。
- [ ] 配對 ≤ 7 天、有可點連結、價格（取自物件本身）≤ 預算 × 容許倍數。
- [ ] 沒有停推訊號、沒有駁回紀錄、沒有送過。
- [ ] 每人今日未滿 1 件、本月未滿 4 件；時段 08–21；預算有額度。
- [ ] 每件都標明 自動送／待審／不可送／本輪暫緩，並附理由。
- [ ] 只有 `sent` 寫去重與扣額度；`held`／`queued` 只佔位、24 小時作廢。
- [ ] 審核當下重驗：在售、價格、連結、客戶狀態、份額。
- [ ] 沒有宣稱已送出；送出屬工具層。

```text

   先送原因：{客戶階段}／{幾天沒出聲}／{新鮮度}

待審（{n} 件；24 小時內沒處理自動作廢）
1. {客戶代碼} × {物件ID}｜待審原因：{原因}

不可送（{n} 件）
- {客戶代碼} × {物件ID}：{關卡編號} {白話理由}

本輪暫緩（不移除，下一輪再評）
- {客戶代碼} × {物件ID}：{今日已 1 件／本月已 4 件／休息時段／額度不足／連結還沒解出}

需補客需（不推、不排審；每週彙整給負責業務）
- {客戶代碼}：缺 {區域／預算}｜建議補問：{一句話問題}
```

## Output requirements（輸出要求）

- 先給四個桶：自動送、待審、不可送、本輪暫緩；再給「需補客需」名單。
- 每件都寫命中哪一條關卡＋白話理由，不能只給分數。
- 讀不出來的欄位寫「讀不出來」，不得用猜的數字湊過關。
- 不出現客戶全名、電話、群名原文；一律用客戶代碼。
- 沒有工具回傳結果之前，不得說「已推」。

## Test cases（測試案例，全部為合成資料）

**T1 — 自動送 vs 超預算 vs 缺連結**：客戶 A001（買、東區、預算 1,000 萬，租戶設自動）。X1 1,050 萬、3 天前、有連結；X2 1,120 萬、2 天前、有連結；X3 980 萬、1 天前、連結還沒解出。期望：X1 自動送（105%）；X2 不可送（112%，也不進待審）；X3 本輪暫緩、不燒去重。

**T2 — 缺預算**：客戶 A002 只說「想在市區買」，沒有預算；配到三件新物件。期望：三件都不可送、不排審；A002 進「需補客需」，建議補問預算上限。

**T3 — 每人份額**：客戶 A003 今天已 `sent` 1 件、本月累計 3 件；本輪又有 2 件合格。期望：兩件都本輪暫緩；明天最多再送 1 件，本月最多再 1 件。

**T4 — 三態與作廢**：X4 自動核准時額度用完 → `queued`；26 小時後仍沒送出。期望：`queued` 期間不寫已推、不算本月件數；超過 24 小時變 `expired` 並留痕；下一輪若仍合格可重新評估。

**T5 — 審核當下重驗**：X5 待審中；按「送」前價格從 1,000 萬調到 1,200 萬（客戶預算 1,000 萬），而且客戶昨天在群裡說「已經買到了，不用再找」。期望：不送；回報兩個原因（超出預算、停推訊號）；X5 不寫已推。

**T6 — 內部收件人**：要送給審核群的「請審核」卡，以及給租戶本人的每日摘要。期望：兩者都不進審核閘、不吃客戶物件額度。

**T7 — 駁回**：X6 給 A004 被駁回；一週後 X6 又配到 A004。期望：直接不可送（駁回黑名單），不再進待審。

**T8 — 賣方群**：群組類型＝賣（屋主），配到一件買方物件。期望：不可送（對象類型不符）。

**T9 — 租金單位**：承租客戶預算「月租 14,000 元」，配到總價 1.4 億的買賣物件。期望：交易別不符，不可送；不得把 14000 當 14000 萬比價。

## Acceptance criteria（驗收標準）

- 同一份輸入，分桶與理由每次都一樣。
- 任何讀不出來的欄位都不會讓物件進「自動送」。
- 超預算、超過 7 天、停推、駁回過、賣方群的物件，不會出現在自動送或待審。
- 只有 `sent` 會寫已推、算份額、扣預算；`held`／`queued` 24 小時後作廢且留痕。
- 內部收件人從不出現在待審清單。
- 輸出不含客戶全名、電話、群名原文，也沒有宣稱已送出。
